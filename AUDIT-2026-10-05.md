# Audit: making Pyto an easy AI-assisted device programming environment

Reviewed 5 October 2026. Scope: the current source tree, installer-generated launcher, agent prompt, UI, program execution, session recovery, examples and tests. This is an audit and implementation proposal; application code was not changed. No iPhone/iPad runtime was available, so native behavior still needs device validation. The workspace exposes no usable Git metadata; this report refers to the supplied files, not a commit.

The largest improvement would be a reliable **ask → build → try → save → run again** workflow. There is already a useful foundation: reusable program files, structured tools, a local API reference, session logs, bounded output, diagnostics and repair. The gaps are concentrated at the boundary between that infrastructure and the person using it.

## Priority findings

### 1. P0 — Repair the chat GUI's API contract and lifetime

Evidence: `harness/ui.py:run_ui`, `_on_main`; `run.py:main`.

The chat window calls `view.present("fullscreen")`. Pyto's documented interface is `ui.show_view(view, mode)`; the current upstream Python wrapper contains no `View.present` implementation. `_on_main` looks for `pyto_ui.main_thread`, also absent from that wrapper. Its fallback calls the callback directly and suppresses exceptions, concealing failures instead of establishing the dispatch guarantee claimed in the module comment.

This is more than “threads are difficult.” The code uses the wrong presentation API and has no coherent window lifetime. Presentation occurs before action handlers are assigned. Merely replacing that line with blocking `show_view` would assign handlers only after dismissal. Conversely, nonblocking presentation lets `run_ui` return and `run.py` close the session and model client while callbacks still need them.

Fix: construct views and wire callbacks first; present last; keep session/client alive for the window lifetime. Implement explicit close and cancellation handling. Verify APIs against the installed Pyto version. Distinguish Pyto's high-level view wrapper from direct UIKit: Pyto explicitly permits modifying its views from another thread; direct UIKit operations require the appropriate native-thread dispatch. Do not put a blocking presentation wait on UIKit's main thread.

Sources: [Pyto UI guide](https://pyto.readthedocs.io/en/latest/library/pyto_ui.html), [upstream UI implementation](https://github.com/ColdGrub1384/Pyto/blob/main/Lib/pyto_ui.py), [mainthread implementation](https://github.com/ColdGrub1384/Pyto/blob/main/Lib/mainthread.py). These are current upstream references, not proof of the user's installed version.

Acceptance: on a real device, open chat, send two turns, dismiss during a request, reopen, rotate and use the keyboard. No frozen presentation, closed-session writes or orphaned callbacks.

### 2. P0 — Serialize in-process programs and track survivors

Evidence: `harness/loop.py:_dispatch` runs up to four tools concurrently; `harness/tools_ios.py:_run_in_process` replaces `sys.stdout`, `sys.stderr`, `sys.argv`, cwd and environment for each program.

Those values belong to the process, not the worker. Two concurrent programs can capture each other's output and restore the wrong globals. A program blocked in native code can outlive the bounded join; its globals stay changed until it exits. A later program can overlap it even if ordinary runs are serialized. User-created child threads and callbacks also escape the parent thread's cooperative trace deadline.

Fix: one managed in-process execution lane, with explicit running/completed/still-running state. If a worker survives its deadline, prohibit another in-process launch until it ends or the user restarts the runtime. Give the user a visible explanation. Make stdout routing and restoration ownership explicit. Keep independent read-only tools parallel, but serialize operations sharing process state, files or native modal UI. This also prevents a batch containing `write_program` and `run_program` racing each other.

Do not promise isolation: generated Python runs with the app's authority. A lock is a concurrency fix, not a security sandbox. Prefer Pyto's own supported script-launch facilities only after checking their lifetime and output semantics on the target version.

Acceptance: concurrent requested runs have separate output and correct arguments; a native-blocked run does not permit a second launch; cwd, environment and streams restore correctly after errors and cancellation.

### 3. P1 — Give generated GUI apps a separate execution workflow

Evidence: `harness/loop.py:SYSTEM_PROMPT`; `harness/tools_ios.py:run_program`; `harness/pyto_api.py` UI reference.

The prompt asks for short, non-interactive programs and requires running them before claiming success. The generic runner defaults to 30 seconds, capped at 300. A useful GUI remains open for user interaction; remaining open is not a failed test. The curated reference already says `show_view` blocks until close, so the agent receives conflicting expectations. The timeout schema also says “Kill the program,” despite the iOS runner's cooperative limitations.

Fix: distinguish batch automation from interactive apps. For an app: validate syntax and imports, test pure logic, launch a preview, capture callback failures, then ask the user to try the meaningful interaction. Report “preview opened” separately from “interaction verified.” Offer Stop/Close and rerun after editing. Do not repeatedly rewrite a functioning app because its view stayed open beyond a batch deadline.

Ship a known-good UI scaffold with layout, background work, error display and cleanup. Correct `harness/pyto_api.py`'s assertion that a plain script already runs on the main thread: Python script execution and UIKit's application main thread must not be conflated.

Acceptance: build a small counter, a form that saves data and a network-backed view; leave each open beyond 30 seconds, exercise actions, close and rerun without false timeout failures or lingering work.

### 4. P1 — Make normal output concise; preserve details on demand

Evidence: `install.py:START_PY` only forwards into `run.py`; `harness/ui.py:Printer.handle` prints every `tool.completed` body regardless of `verbose`.

The noisy behavior attributed to `start.py` originates in the shared event renderer. API reference results, file contents, program output and completion summaries all compete with the answer. Changing only the launcher would not fix both front ends. A direct probe confirmed that a 100-line tool result produces 101 lines with `verbose=False`.

Recommended normal display:

```text
Creating your clipboard notebook…
Saved clipboard_note.py
Test: one note saved successfully

Ready. Run “Clipboard notebook” to save what you copy.
[Run again] [Edit] [Details]
```

Keep one short status per meaningful operation, concise actionable errors, output artifacts and one final answer. Put arguments, reference material, raw tool results and timings behind Details or verbose mode. Keep approval information visible when a decision is needed; concise output must not obscure the proposed action.

Also fix `Printer`'s partial buffer: `message.completed` adds the full message without clearing `_partial`. A probe produced `hello\nhello` after one streamed message. This affects the `Transcript` model; the live GUI currently uses a separate text stream. `_UIStream` itself continually copies the whole view text, has no display-size bound and flushes for every write. Coalesce updates, cap rendered history and provide scrollback from the session log. Fixed frames need layout/keyboard handling on device.

Acceptance: a large `pyto_api` result occupies one normal status line; details remain accessible; final answers appear once; long sessions remain responsive.

### 5. P1 — Provide approvals inside the GUI

Evidence: `run.py:main` always constructs `TerminalApprover`; `make_options_factory(ui=True)` marks the session interactive but does not substitute a UI approver. `TerminalApprover` checks `stdin.isatty()`.

A visible chat window therefore does not guarantee that the user can answer an approval. With non-TTY stdin, the request is denied; otherwise it asks through the console, outside the chat workflow. The denial suggests `--yolo`, which is an unnecessarily broad escape hatch for an interaction problem.

Fix: a GUI approval card with action, relevant arguments, Allow and Deny. Resolve the pending request asynchronously, and deny it if the window closes. Test the actual Pyto console's input behavior separately; desktop TTY detection is not proof that an iOS user is absent.

Acceptance: share-sheet and URL requests can be approved or denied entirely within chat, without enabling blanket approval.

### 6. P1 — Recover interrupted tool calls before resuming conversation

Evidence: `harness/session.py:_prune_orphan_tool_messages`, `project`; `harness/loop.py:run_turn`, `_dispatch`.

Projection drops undeclared tool results, but leaves assistant tool calls with missing results. A direct probe confirmed an assistant declaration survives with no matching tool message. The assistant row is saved before execution; tool messages are appended after the batch completes. An app kill in that interval leaves incomplete provider history and uncertain side effects. A valid JSONL prefix is not necessarily a valid resumable conversation.

Fix: journal each call's intent and completion durably. On resume, reconcile every declared call. Represent interruption explicitly in provider history, and tell the user when the action's outcome is unknown. Do not automatically replay calendar writes, file mutations or other side effects merely because a result is missing. Persist finished calls as they finish instead of waiting for the slowest call in the batch.

Acceptance: simulate interruption before a tool, during it and after the side effect but before logging. Resume produces valid message history and no duplicate side effect.

### 7. P2 — Preserve project context and make reuse discoverable

Evidence: `harness/session.py:compact` drops older events without a semantic project summary; `harness/budget.py` limits disk/event counts rather than provider context tokens; `open_session` starts a new session unless resume is explicitly requested. Existing examples focus on three scripts and require users to handle paths/arguments.

Recommendation: add a small program library with title, purpose, entry file, required capabilities, inputs, last verification result and Run/Edit actions. Store a durable project brief describing the user's decisions and current files. Update that brief at checkpoints so compaction or a new chat does not erase product intent. Budget actual request context independently of disk-log size.

Provide forms and file pickers for routine inputs, rather than making phone users edit `sys.argv`. A saved app should be usable without another model request. Add an optional Shortcut handoff after the foreground workflow works reliably.

Acceptance: a novice can create a tool, close Pyto, return later, run it and ask for a revision without locating paths or reconstructing the original conversation.

## Prompt changes after the runtime supports them

Keep the valuable instructions to consult `pyto_api`, save reusable files, report actual outcomes and diagnose repeated failures. Replace the universal non-interactive rule with a batch/app distinction. Avoid platform claims that are rendered unconditionally even in desktop mode. Give the agent a concise task workflow:

1. Determine whether the user wants a one-time action or a reusable app; infer when obvious.
2. Inspect the relevant files and installed capabilities. Consult only the needed API references.
3. Build from a verified scaffold, with data persisted in the workspace.
4. Test pure logic safely; preview interactive behavior through the supported app runner.
5. Report the exact verification achieved, register the saved program, and provide Run/Edit actions.

Use execution policy to enforce constraints. More prompt prohibitions cannot fix missing runtime lifecycle support or a console-only approval interface.

## Delivery order and verification

First fix the GUI contract/lifetime and shared-process execution ownership. In the same early release, make output concise and add GUI approvals. Then deliver interactive preview and interruption recovery. Finally add the program library, durable project briefs and Shortcut packaging.

Add strict Pyto API contract tests: permissive mocks that invent `present` or `main_thread` would preserve the defects. Current searches found no tests exercising `run_ui`, `_on_main` or `_UIStream`; existing Printer coverage does not establish the GUI lifecycle. Test state transitions and competing executions on the desktop, then run a small real-device acceptance matrix. Desktop green tests cannot prove UIKit compatibility, keyboard behavior, permissions or app suspension handling.

Use five user tasks as release gates: clipboard notebook, selected-folder file organizer with preview/undo, persistent counter, network-backed form, and a tool that requests a device permission. Measure successful completion, recovery after interruption, number of manual code/path edits and time to run the saved tool again. These measures are more useful to the stated goal than tool count alone.

Validation: `python3 -m unittest discover -s tests -t .` passed all **717 tests** in 38.849 seconds with localhost access for the mock provider. The restricted sandbox prevented socket creation; the successful run used the same suite with that restriction lifted. An earlier invocation omitted `-t .` and caused relative-import errors; those are invocation errors, not product defects. Focused probes also verified verbose-off output expansion, the uncleared transcript partial buffer and projection retaining an unresolved tool call. Native GUI findings are source/documentation comparisons, not on-device reproductions. No production API requests or application-code edits were needed.

## Implementation update — goal 02

The chat GUI finding above has since been implemented for v1.0.7. Presentation now uses Pyto's documented `ui.show_view`, actions are wired before presentation, turns run on a worker, and dismissal cancels/drains the active worker before `run.py` closes the session and client. Stop, Close, callback lifecycle and strict API-contract coverage are documented in [goal 02](harness/projects/easy-device-programming/goals/02-working-chat-gui.md). The implementation was checked against the [Pyto UI guide](https://pyto.readthedocs.io/en/latest/library/pyto_ui.html) and Pyto's upstream module; the installed Pyto version and native device behavior remain unverified. See [v1.0.7 release notes](RELEASE-NOTES-v1.0.7.md) for test results and the device checklist.

## Implementation update — goal 03

Goal 03 is implemented in the local v1.0.9 candidate (unpublished). Pyto in-process runs now own a managed execution lease until shared interpreter state is restored. A run that survives its deadline blocks conflicting launches and workspace access until it exits; the result explains the uncertain side effects and restart recovery. Program-created threads are observed and joined before restoring shared streams and cwd. Batch dispatch orders writes before dependent reads/runs and leaves independent reads parallel.

The prior candidate validation passed **768 tests**. This container's normal `asyncio.run()` shutdown stalled after thread-pool work, so tests used a small periodic-wake wrapper around the same async test bodies. The mock provider's ephemeral localhost server ran with the sandbox restriction lifted. Goal 03's Pyto device checklist remains pending; desktop results do not establish native-call, thread or app-suspension behavior. See [Goal 03](harness/projects/easy-device-programming/goals/03-safe-program-execution.md) and the local [v1.0.9 candidate notes](RELEASE-NOTES-v1.0.9.md).

## Implementation update — goal 04

Goal 04 is implemented in the same unpublished local candidate. Visible GUI approvals use the existing policy, show action descriptions and arguments, queue concurrent prompts, and reject stale or repeated answers. Stop and Close deny pending actions. Desktop coverage drives share and URL decisions through `make_policy`; the allowed action runs once and the denied action does not run. Terminal and headless policy paths remain unchanged. The [Pyto device checklist](harness/projects/easy-device-programming/goals/04-in-app-approvals.md#pyto-device-checklist--pending) remains open.

At the Goal 04 checkpoint, the local candidate passed **773 tests** and its focused GUI/printer/policy suite passed **35 tests**. The tests use a localhost mock provider; the run received permission to bind loopback sockets after the default sandbox rejected them. No Pyto device was connected.

## Implementation update — goal 08

The unpublished candidate now journals tool intent before scheduling, actual start immediately before a handler, and each completed provider result in one durable event. Recovery inserts explicit “not run” or “outcome unknown” messages into valid provider history and does not replay missing calls. Old `message.tool` logs remain supported. Partial batch, prelaunch, uncertain side-effect and strict-provider tests pass. The combined full suite passed **779 tests** and focused Goal 08 loop/session coverage passed **73 tests**. The [Goal 08 device checklist](harness/projects/easy-device-programming/goals/08-interruption-recovery.md#pyto-device-checklist--pending) remains open.

## Implementation update — goal 05

The same unpublished local candidate now includes a dedicated `preview_program` lifecycle for
interactive PytoUI apps. Static syntax/import availability checks precede execution; interactive
views do not use the bounded batch timeout. Guarded callbacks report successful interactions and
callback errors, and closing the view signals app-owned work to stop. Survivors are reported and
retain the process lease. The reusable scaffold covers a saved counter/form, background network
request, visible errors and cleanup, with pure logic separated for short checks.

The full desktop suite passed **790 tests** in 85.282 seconds, including a simulated preview left
open for 30.1 seconds, mocked network data and cleanup/survivor checks. `stdlib_audit.py --json`
reported `ok: true`. The Goal 05 Pyto device checklist remains open because this host has no
connected iOS app session or simulator; these desktop results do not prove native presentation,
callbacks or iOS lifecycle behavior. See [Goal 05](harness/projects/easy-device-programming/goals/05-interactive-preview.md).

## Implementation update — goal 06

The same local candidate now includes a versioned saved-program library. Registration records the
program's title, purpose, workspace-relative Python entry file, batch/app mode, required
capabilities and latest verification. Metadata writes are private and atomic; malformed indexes
are preserved for inspection, title collisions are refused, and user source files remain in place.
The chat Programs button and `/programs`, `/run ID` and `/edit ID <requested change>` commands
provide discovery and use. The terminal supports the same commands, while `--programs` and
`--run-saved ID` work without an API key or model call. Edit carries the selected program context
so the agent can read the chosen source before revising it.

After Goal 06 the full desktop suite passed **811 tests** in 86.083 seconds. Focused coverage
includes persistence, malformed metadata, duplicate titles, missing and renamed files, verification
updates, model-free execution, CLI no-key behavior and chat/terminal commands. `py_compile` passed
for the changed runtime files and `stdlib_audit.py --json` returned `ok: true`. The Pyto restart,
chat-window and launcher acceptance checks remain pending; see [Goal 06](harness/projects/easy-device-programming/goals/06-saved-program-library.md#pyto-device-checklist--pending).
